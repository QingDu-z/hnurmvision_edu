## 2. 两个必须先定的判断

### 2.1 "二选一"和"训练产物"冲突吗

课件把两件事分开写：

- 任务 1：**实现方式**二选一（OpenCV 或 NN）；
- 任务 2：交**训练产物**，且没写"若选 NN 方案"。

**最坏解释**：即使检测用传统视觉，也要把训练流程跑通并交产物。
**最好解释**：任务 2 是给选 NN 的人准备的。

**稳妥策略**（我建议）：按最坏解释做，成本只多 6–8 小时，但两种情况都不失分：

```text
任务1：传统视觉实现 lesson03（交付录屏）
任务2：用 dataset 的 10% 子集训一个 YOLO-Pose（4 关键点）小模型，交产物
```

而且这条路线还顺带给了你一个"NN 对照组"：同一批仿真截图，传统 vs Pose 模型，谁的检出率高，数据说话。

### 2.2 域差异：训练用真实素材，考核用仿真渲染

〔实测〕我抽了 4 张训练图，都是真实赛场（场馆横幅、观众、夜场户外），分辨率 1920×1080 / 1280×768 / 640×480 混杂；同时有少量 1440×1080（与仿真器出图一致）。

这意味着：

| 现象 | 后果 |
|---|---|
| 在真实图上调的传统阈值 | 搬到仿真图上会失效（仿真器 LED 被 `armor_emissive_scale=3.0` 提亮到灰度 ~195） |
| 在真实图上训的 Pose 模型 | 在仿真图上可能掉点（亮度分布、材质、噪声 `noise_sigma=2.0` 都不同） |

**缓解手段（按性价比排序）**：

1. **传统视觉的阈值直接在仿真图上调**（只需仿真图，不需要数据集）；
2. 用仿真器自带的 `DatasetPlugin` 导 200–500 张仿真图（带标注），做 Pose 模型的**验证集**，必要时微调几个 epoch；
3. 任务 2 的产物按"真实数据集训练"交付（这是课件给的数据，符合要求），但**在 README 里写清楚"考核环境为仿真，已用 N 张仿真图验证/微调"**——这属于加分项。

### 2.3 融合架构（方案 B）：传统做几何，网络做语义

```text
每帧（约 3 ms）
  └─ 传统管线：通道分离 → 阈值 → 形态学 → 灯条 → 两两配对 → 候选（外接框 + 4 角点）
        └─ 每个候选（约 0.5 ms/个）
              └─ 语义分类器（48×48 灰度）
                    ├─ 判为"背景" → 丢弃该候选（抑制反光/旋转靶误检）
                    └─ 判为"某号装甲板" → 写入 class_id / confidence
输出：std::vector<Armor>（角点来自传统，语义来自网络）
```

**为什么是这个分工**：

| 环节 | 谁做 | 理由 |
|---|---|---|
| 找灯条、配对、算四角点 | 传统 | 纯几何、可解释、CPU 上 3 ms 内完成；调参时每一步都能存图看 |
| 判"这块板是几号/是真是假" | 小分类器 | 传统做语义只能靠模板匹配，换视角就废；48×48 小网络在 CPU 上 0.2–0.5 ms |

**与任务 2 的关系（关键，别做重复工）**：

| 产物 | 用途 | 硬要求？ |
|---|---|---|
| YOLO-Pose 模型（14 类 / 4 关键点） | 任务 2 的 `best.pt`/`last.pt`/mAP 曲线 | **是**（课件原文） |
| 语义分类器（48×48，2–15 类） | 方案 B 的"语义"环节 | 否，但它是方案 B 的核心 |
| 可选：Pose 模型低频兜底 | 传统连续 N 帧零检出时，整帧跑一次 Pose | 否，加分项 |

注意：分类器给的是 **accuracy / 混淆矩阵**，没有 mAP——所以任务 2 那份 mAP 曲线**必须**来自 Pose 模型，两者不能混。稳妥顺序是：先把 Pose 训练流程跑通（满足硬要求），再做分类器（完成方案 B）。

GT 可视化脚本（10 行，验证标签没转置/没归一化错）：

```python
import cv2, numpy as np, pathlib
base = pathlib.Path.home() / "hnurmvision_edu/dataset/train"
for img_p in sorted((base / "images").glob("*.jpg"))[:20]:
    im = cv2.imread(str(img_p)); h, w = im.shape[:2]
    txt = (base / "labels" / (img_p.stem + ".txt"))
    if not txt.exists(): continue
    for line in txt.read_text().split("\n"):
        v = line.split()
        if len(v) < 13: continue
        pts = np.array([[float(v[5+i*2])*w, float(v[6+i*2])*h] for i in range(4)], np.int32)
        cv2.polylines(im, [pts], True, (0, 255, 0), 2)
    cv2.imshow("gt", cv2.resize(im, (960, 540)))
    if cv2.waitKey(0) == 27: break
```

**门槛**：绿色四边形的四个顶点都贴在装甲板四角上（若整体偏移，说明坐标顺序或归一化理解错了）。

### P1 传统最小闭环（4 h）

管线固定为五步，先求"能框住"，不求美：

1. **通道**：红/蓝装甲用 HSV 或 BGR 通道分离（仿真图蓝方亮，先按你队伍颜色做）；
2. **阈值**：仿真器 LED 灰度约 195（`armor_emissive_scale=3.0` 的作用），阈值可从 150 起步；
3. **形态学**：开运算去噪 + 闭运算连断；
4. **灯条筛选**：`findContours` → 面积、长宽比（细长）、角度；
5. **配对成板**：两灯条同高、间距在合理范围、中间亮度可验证 → 外接矩形 + 四角点。

调试方式：每一步 `cv::imwrite` 存一张图，看阈值图/轮廓图，不要盲调。

### P2 角点排序 + 评估（2 h）

- 排序规则：按 y 分组（上下两条边），每边按 x 排，得到"左上、右上、右下、左下"；
- 评估脚本：用 P0 的 GT，算
  - 检出率 = 匹配上的 GT 数 / GT 总数（IoU > 0.5 视为匹配）；
  - 角点误差 = 四个角点平均欧氏距离（像素）。

> 这一步的产出是**数字**，不是感觉。后面无论调参还是换 NN，都用它比较。


### P2 实测结果（2026-11-05，仿真器 Digit1 导出的 53 帧）

| 指标 | 全量 GT（163 块） | ≥30 px 的 GT（53 块） |
|---|---|---|
| 检出率 recall | 32.5% | **100%** |
| 准确率 precision | 100% | **100%** |
| 角点平均误差 | 2.06 px | 2.06 px |

**怎么读这组数**：GT 包含 3–4 块/帧，但其中 43.6% 的板宽 < 15 px（侧板、远处板），中位数只有 22 px。按“3 m 正面目标（≈68 px）”口径，53 块全部检出；全量 recall 低是因为分母里塞了肉眼都难分的侧板。

**P2 期间修掉的一个误检**：场地青色亮线在拐角处被当成两块灯条配上对（见 `dump/frame_000001.jpg` 底部的小绿框）。加两条约束后 precision 从 50% → 100%，但分组对照实验表明**真正起作用的是第 2 条**：

1. `kBarMaxTiltDeg = 20`：灯条长轴必须接近竖直（用 `minAreaRect` 判定，横/斜的场地线被排除）——**这条是关键**；
2. `kPlateMinHeightPx = 14` / `kPlateMaxHeightPx = 216`：板高区间，属无害兜底（单独去掉它指标不变）。

> 参数取值迭代过程：最初是 16/140 px，扫描实验发现上限 140 零收益且会在 <0.51 m 误杀近处板，因此放宽到 216。详见 §10.4。

**关于阈值单位（一个容易搞错的点）**：板高阈值用**像素**而不是“图像高度比例”，因为这两者对上游处理的鲁棒性相反——ROI 裁剪不改变 px/m，像素阈值仍然有效；而 resize 会改变 px/m，比例阈值才正确。本函数接口只有图像、拿不到内参，所以选择绑定像素，并在注释里写明“按 1080p/fy=1303.7 标定，换分辨率需重标定”。

> `minAreaRect` 在 OpenCV 4.5 的角度语义容易写错：`angle ∈ [0,90)`，长轴方向要按 `size.width >= size.height ? angle : angle + 90` 换算。我用三段合成数据（竖条/横条/斜 30°）验证过。

### P3.5 标签角点顺序规范化（1 h，一次性）

**为什么必须做**：`lesson03` 要求 `corners` 是「左上、右上、右下、左下」（图像坐标），而数据集标注是「板体顺序」——实测 11564 个实例里 **10027 个（86.6%）不是这个顺序**（最常见的是 `左上,左下,右下,右上`，占 8848）。直接训练，模型学到的就是这套不一致的顺序。

**工具**：`tools/normalize_labels.py`（不改原数据，输出到 `dataset_norm/`）

```bash
python3 tools/normalize_labels.py --dry-run          # 先看统计，不写文件
python3 tools/normalize_labels.py                    # 复制图片 + 写规范化标签
python3 tools/normalize_labels.py --link             # 图片用软链，省 683 MB
```

```text
前 3 种绕序：TL,BL,BR,TR 8848 / TL,TR,BR,BL 1085 / TR,BR,BL,TL 951
```

**算法**：先按 y 分上下排、各自按 x 分左右；若上排两点几乎同高（窄板/正对镜头）则退化为极角排序；两种绕向里挑满足 `TR.x>TL.x、BR.y>TR.y、BL.x<BR.x、TL.y<BL.y` 的那个——这样横滚、倒装的板也能摆正。残余 6 个（0.05%）是四点几乎共线的极端样本，可忽略。

**验证**：

```bash
python3 tools/vis_gt.py --root ~/hnurmvision_edu/dataset_norm --n 20 --out /tmp/gt_norm
# 或统计绕序
python3 tools/vis_gt.py --root ~/hnurmvision_edu/dataset_norm --order-check
```

**实测（`--order-check` 全量扫描 train 的 9202 个实例）**：

| 数据集 | 严格合规（四条不等式） |
|---|---|
| 原始 `dataset/` | 1228/9202 = **13.34%** |
| 规范化后 `dataset_norm/` | 9198/9202 = **99.96%** |

残余 4 个是四点几乎共线的极端样本，可忽略。

> 注意别用"质心法"看合规率：窄板正对镜头时，上排两个角都落在质心同侧，会被统计成 `TL,TL,BR,BL` 之类的退化组合，但它并不违反四条不等式。`vis_gt.py --order-check` 已改为严格判据 + 全量扫描。

**门槛**：严格合规率 > 99%（当前 99.96%）。

> 训练时把 `data.yaml` 的 `path` 指向 `dataset_norm`，图片可以是软链（ultralytics 能正常读）。

## 10. 值得向考官说明的工程决策

> 这一节是"答辩稿"：面试或验收时被问到的每一个数字、每一个参数，都能在这里找到出处和实验依据。

### 10.1 为什么主体用传统视觉，而不是直接上神经网络

| 理由 | 依据 |
|---|---|
| 迭代速度 | 传统改一次参数 → 重编 20 s → 立刻看到 recall 变化；NN 要训练、导出、集成 |
| 可解释性 | 每一步都能存图（阈值图、灯条框、配对结果），出问题定位到具体参数 |
| 运行成本 | 传统单帧 3 ms 内，远低于 28 ms 预算；NN（CPU）YOLOv5s 约 60–100 ms |
| 仿真器就是按传统可做设计的 | `config.toml` 里 `armor_emissive_scale = 3.0` 的注释：LED 灰度提到 ~195，正是为了让灯条阈值（150）能触发 |
| NN 仍然做了 | 任务 2 硬性要求训练产物（YOLO-Pose）；方案 B 里再训一个 48×48 分类器补"编号/真假"语义 |

一句话：**传统负责 where（几何），网络负责 what（语义）**，两者不是二选一，而是分工。

### 10.2 检测指标（务必带口径，否则会被追问）

```text
数据：仿真器 DatasetPlugin 导出 53 帧（按住数字键 1，4 Hz）
GT：163 块装甲板（每帧 3–4 块，含侧板/远处板）
```

| 指标 | 全量 GT（163 块） | ≥30 px 的 GT（53 块） |
|---|---|---|
| recall | 32.5% | **100%（53/53）** |
| precision | **100%** | **100%** |
| 角点平均误差 | 2.06 px | 2.06 px |

**为什么两个口径都要报**：GT 里 43.6% 的板宽 < 15 px（中位数 22 px），是斜视侧板和 50 m 外的停泊靶。3 m 正面目标约 68×28 px，对应 53 块，全部检出。
**只说 32.5%** 显得算法差；**只说 100%** 会被问"分母是什么"。标准答法：*"3 m 正面目标 53/53 = 100%；全量 32.5%，因为 GT 含 <15 px 的侧板。"*

### 10.3 参数表与物理依据

| 参数 | 值 | 依据 |
|---|---|---|
| `kBinThreshold` | 150 | 仿真 LED 灰度 ~195（`config.toml` 注释），留 45 的余量 |
| `kBarMinHeight` / `kBarMinAspect` / `kBarMaxAspect` | 8 px / 1.6 / 12 | 3 m 处灯条约 24×4 px；更细的是反光条 |
| `kBarMaxTiltDeg` | 20° | 装甲板在车上是竖直的；场地亮线常横/斜 |
| 配对：高度差 / 中心 y 差 / 间距比 | 35% / 55% / 0.8–5 | 同一块板的两根灯条几何一致；比例形式，与分辨率无关 |
| `kPlateMinHeightPx` / `kPlateMaxHeightPx` | 14 / 216 px | `h_px = fy·0.055/Z`，fy=1303.7 → 5 m≈14 px、0.4 m≈216 px |
| `kLargeArmorAspect` | 3.2 | 小装甲板 135×55 ≈ 2.45，大装甲板 225×55 ≈ 4.1 |
| 板面验证 `kFaceThrRatio` / `kFaceRatioLo..Hi` | 0.30 / 0.03–0.70 | 两灯条之间必须有"数字"亮斑：误配帧中间均值 3.2、最大 12，而灯条均值 145；真板数字亮像素占比实测 0.30 |

**为什么只有板高用像素、其余用比例**：这是刻意为之，理由见 §10.5。

### 10.4 四个实验，四个结论

| 实验 | 做法 | 结论 |
|---|---|---|
| 板高上下限是否有效 | 4 组 min/max（16/140、16/9999、13/9999、12/9999） | 指标完全不变 → **上限 140 是零收益参数**，且会在 <0.51 m 误杀 → 改成 216 |
| 到底是谁干掉了场地线误检 | 只加高度过滤 vs 加倾斜过滤 | 只加高度过滤时 precision 仍 50%；**倾斜过滤才是关键**，高度过滤只是兜底 |
| `minAreaRect` 角度语义 | 竖条/横条/斜 30° 三段合成数据 | OpenCV 4.5 的 `angle ∈ [0,90)`，竖条和横条都可能报 90°；长轴方向须按 `width>=height ? angle : angle+90` 换算 |
| 分辨率断言是否生效 | 把帧缩到 720×540 再跑 | 打印一次警告且不崩溃；1440×1080 下静默通过 |
| 比例带能否挡住"跨板误配" | 实测误配帧：板宽 78 px、板高 20 px、比例 3.9 | **挡不住**：3.9 与大装甲板 4.1 几乎重合 → 必须靠板面验证 |
| 板面验证是否误伤真板 | 53 帧回归 + 数字亮像素占比实测 0.30 | 未误伤（recall 仍 100%），阈值取 0.03–0.70 有余量 |
| 评估口径的取整是否影响结论 | 同一批 B 组：浮点包围盒 66 块 vs 整数包围盒 68 块 | 分母差 2 块，recall 从 67.6% 变 69.7% → 必须统一为浮点 |

### 10.5 为什么阈值绑定像素，而不是"图像高度比例"

曾试过 `ratio × image.rows`，但它有一个隐蔽缺陷：

| 上游动作 | px/m | 比例阈值 | 像素阈值 |
|---|---|---|---|
| ROI 裁剪 | 不变 | 阈值被放宽（错） | 正确 |
| resize / 换相机 | 变化 | 正确 | 需重标定 |

而**仅凭 `image.rows` 无法区分这两者**（两种情况行数都变小），接口里又没有内参，所以任何自动换算都会在一种情况下出错。选择绑定像素，是因为"裁剪"是后续提速最可能引入的处理；同时加了**分辨率断言**，把 resize/换相机的失效从"静默变松"变成"一行可见警告"。

真要两者都对，得把内参传进来（`lesson03_set_intrinsics(fx, ...)`，`min_h = fx·0.055/Z_max`）——这是预留的升级路径，当前不动是为了不改课程规定的接口。

### 10.6 踩过的坑（都能复现）

| 坑 | 现象 | 处理 |
|---|---|---|
| `cv::polylines` 只接受整点 | 传 `vector<Point2f>` 直接 `terminate`：`(-215:Assertion failed) p.checkVector(2, CV_32S) >= 0` | 先 `cvRound` 转 `cv::Point` |
| 场地青色亮线被当成灯条 | 画面底部多一个假框，precision 50% | 倾斜角过滤（≤20°） |
| 相邻两块板的灯条互相配对 | 绿框跨在两块板之间；几何比例 3.9 与大板 4.1 重合，比例约束无效 | 板面验证（两灯条之间必须有数字亮斑） |
| 闭运算核过大 | 灯条被糊成一片，配对失败 | 竖向 `3×5`，只连竖断 |
| 评估分母不设门槛 | recall 32.5% 误判为"算法差" | 报指标必须带尺寸口径 |

### 10.7 可复现（三条命令）

```bash
# 1) 采集带 GT 的仿真帧（仿真器窗口里按住数字键 1 约 10 s）
#    产物：simulation/simulator/dataset/{images,label}/
# 2) 编译评估工具
./scripts/build_training.sh
# 3) 算指标（自动输出两个口径，不需要额外参数）
./build/eval_detect simulation/simulator/dataset
```

输出形如：

```text

>=30px GT    GT  53 / 检出 53 / 匹配 53 | recall 100.0% | precision 100.0% | 角点 2.06 px
```

**验收看第二行**（>=30 px 即 3 m 正面目标口径）；第一行是全量，用来解释“为什么不是 100%”。

`eval_detect` 的判定逻辑：GT 与检出按**外接框 IoU ≥ 0.5** 贪心匹配；角点误差在把双方都排序成 `TL,TR,BR,BL` 后逐点算欧氏距离。GT 为 10 列（`color typ label` + 4 个归一化角点），与训练用的 13 列 YOLO-Pose 格式不同，解析代码里已分别处理。

### 10.8 当前局限（主动说明，别等被问）

1. 只验证了静止靶；平移/旋转靶需按 `F6` 切换后单独采样；
2. 阈值 150 是固定值，强曝光变化下会失效（后续可改自适应分位数）；
3. 大/小装甲板用宽高比判定，远距离时 2.45 与 4.1 的区分会变糊；
4. `class_id` 恒为 `-1`（课件允许），编号要等 P4.5 的分类器；
5. 远于 5 m（<14 px）故意不检，是设计取舍而非缺陷；
6. 板面验证要求"数字可辨"，等效有效距离约 10 m 以内；更远时数字不足 3 px，候选会被拒绝。

### 10.9 传统 vs NN：同一批仿真帧上的对比（2026-11-08）

三组仿真数据（1440×1080，GT 由仿真器导出）：A 3 m 静止 48 帧、B 旋转靶 46 帧、C 近距 41 帧。
口径统一：GT 宽度 ≥30 px（浮点包围盒）、IoU ≥ 0.5、一一匹配。

| 场景 | 方法 | ≥30px GT | 检出 | 匹配 | recall | precision |
|---|---|---|---|---|---|---|
| A 3 m | 传统 | 48 | 48 | 48 | **100%** | **100%** |
| A 3 m | NN (conf .25) | 48 | 49 | 48 | **100%** | 98.0% |
| B 旋转 | 传统 | 66 | 46 | 46 | 69.7% | **100%** |
| B 旋转 | NN (conf .25) | 66 | 73 | 64 | **97.0%** | 87.7% |
| B 旋转 | NN (conf .55) | 66 | 51 | 51 | **77.3%** | **100%** |
| C 近距 | 传统 | 41 | 41 | 41 | **100%** | **100%** |
| C 近距 | NN (conf .25) | 41 | 41 | 41 | **100%** | **100%** |

**两个必须一起说的事实**：

1. **NN 的框不能直接用**：模型输出的 box 高度约为 GT 的 **1.90 倍**、宽度 1.09 倍
   （训练集标注的框包含装甲板外框，仿真 GT 只标板面），IoU 中位数 0.483，
   按 IoU≥0.5 计算 **box mAP = 0**。上表 NN 一栏是把**四个角点重算包围盒**后得到的——
   也就是说：**角点准、框偏大**。
2. **NN 在斜视上明显更强**：B 组 recall 97.0%（conf .25）或 77.3%（conf .55，precision 100%），
   而传统只有 69.7%（原因见 §11.4：斜视时单侧灯条被遮挡，几何无法配对）。

**结论**：融合的价值在"斜视补检 + 语义"，不在"取代传统"：
- 传统：零误检、角点 1.62 px、单帧 ~3 ms，是交付主路径；
- NN：补 B 类场景漏检、提供 14 类语义，但需按角点使用、不能信任其 box。

**类别映射注意**：仿真器的 `label` 字段是 **1 基编号**（1..5），转 YOLO 时须用
`cls = (label-1) + 7*color`；用 `label + 7*color` 会让全部类别偏一位，mAP 直接归零。

### 10.10 融合原型：从 Python 验证到 C++ 落地（2026-11-08）

**先量化价值，再写代码**。用 `tools/fuse_proto.py` 在仿真三组数据上验证（NN conf=0.4）：

| 组 | 传统检出 | 拿到类别 | 类别正确 | 覆盖率 | 准确率 | NN 独有的真目标（补检收益） |
|---|---|---|---|---|---|---|
| A 3 m | 48 | 48 | 48 | 100% | 100% | 0 |
| B 旋转 | 46 | 46 | 46 | 100% | 100% | **13** |
| C 近距 | 41 | 41 | 41 | 100% | 100% | 0 |

B 组融合后：46 + 13 = 59 / 66 → **recall 89.4%**（纯传统 69.7%），且 13 块全部命中 GT，
precision 仍 100%。**结论：融合的价值在“斜视补检 + 语义”，不在取代传统。**

**C++ 落地要点**：

1. 传统 `lesson03_detection` 仍是主检测器，融合只负责补 `class_id` 与补检；
2. ONNX Runtime 推理，输入 RGB、letterbox 640，关键点映射 `(x - pad) / scale`；
3. **用四个关键点重算包围盒**（模型 box 高度约真实板框 1.9 倍）；
4. 与传统框按 IoU ≥ 0.3 匹配 → 填 `class_id`；未匹配且 `conf ≥ 0.55` 才补检；
5. 补检前与已有框做 IoU > 0.20 去重，避免重复标签。

**代价**：每 N 帧一次推理（N=5 时约 +3.7 ms/帧均值），斜视场景因补检存在会略高。

### 11.3 采集多组仿真数据时的坑（2026-11-08 实测）

仿真器把数据写到**启动时的工作目录**下的 `dataset/`（源码里是相对路径 `DatasetWriter::new("dataset")`，
`run_simulator.sh` 会先 `cd simulation/simulator`）。想采多组数据做对比，就得把 `dataset/` 改名。

**坑**：在仿真器**运行中**执行 `mv dataset dataset_A_3m`，写盘路径消失，进程直接 panic：

```text
thread 'Async Compute Task Pool (0)' panicked at src/dataset/prelude.rs:245:56:
called `Result::unwrap()` on an `Err` value: Os { code: 2, kind: NotFound, ... }
```

**正确顺序**：

```text
1. 按住数字键 1 采样
2. 松开 1，等 1–2 秒（让队列里最后几帧落盘）
3. Ctrl+C 关闭仿真器        ← 必须
4. mv dataset dataset_<场景名>
5. 重新启动仿真器（自动重建 dataset/）
```

**崩溃后自查残帧**（只有图没有标签的帧要删掉）：

```bash
cd simulation/simulator
for f in dataset_A_3m/images/*.jpg; do
  b=$(basename "$f" .jpg)
  [ -f "dataset_A_3m/label/$b.txt" ] || echo "缺标签: $b"
done
```

**顺带**：`ls -d dataset*` 会把 `dataset_53f`、`dataset_A_3m` 一起匹配出来（`*` 匹配任意后缀），
所以不能用它判断“旧的 dataset 是否已改名”，要看 `[ -d dataset ]`。

### 11.4 旋转靶漏检的归因实验（2026-11-08）

三组仿真数据（A 3 m 静止 48 帧 / B 旋转靶 46 帧 / C 近距 41 帧）评估结果：

| 组 | ≥30 px GT | 检出 | recall（≥30 px） | precision | 角点误差 |
|---|---|---|---|---|---|
| A 3 m 静止 | 48 | 48 | **100%** | 100% | 1.62 px |
| B 旋转靶 | 66 | 46 | **69.7%** | 100% | 3.52 px |
| C 近距 | 41 | 41 | **100%** | 100% | 3.63 px |

B 组漏检 20 块。用探针逐帧统计"每块 GT 板周围能检到几根灯条"：

```text
A 组：2 根 48/48（全部成对）
B 组：2 根 48 | 1 根 18   ← 18 块板只剩一根灯条
C 组：2 根 41/41
```

**参数扫描全部无效**（recall 恒定 69.7%）：

| 变量 | 扫描范围 | 结果 |
|---|---|---|
| 竖向闭运算核高 | 5 / 9 / 13 / 17 / 21 | 无变化，≥17 开始引入噪声误检 |
| 灯条最小高度 | 8 / 6 / 4 / 3 px | 无变化 |
| 灯条长宽比上限 | 12 / 16 / 20 / 26 | 无变化 |
| 二值化阈值 | 150 / 130 / 110 / 90 / 70 | 46→47 块（+1），阈值 70 时误检 15 |

**结论**：斜视时其中一根灯条在渲染上被板体遮挡，只剩零星亮段——单灯条无法配对，属几何/物理极限，
不是参数问题。因此"必须看到两根灯条才能配对"的传统方案，在偏航约 60° 以外必然失效。

**交付表述**：偏航 > 60°（图像宽高比 < 1.35）的装甲板不纳入交战包线；该姿态下 PnP 位姿误差
同样过大。若比赛需要覆盖侧向目标，正解是第四讲的跟踪（用相邻帧补检），而非继续调阈值。

### 11.5 评估口径的取整 bug（2026-11-08 实测）

现象：同一批 B 组数据，探针算出 `>=30px GT = 66`、recall 69.7%，而 `eval_detect` 报 `68`、67.6%。

原因：`tools/eval_detect.cpp` 的 `bbox()` 用了 `cv::boundingRect(vector<Point2f>)`，
它的返回值是**整数** `cv::Rect`，宽度按 `ceil(max) − floor(min)` 计算，比真实宽度多 0–1 px。
于是真实宽度 29.x px 的板被算进 “>= 30 px” 口径，分母多了 2 块且都没检出，recall 被拉低。

**修法**：改成浮点包围盒（`max − min`），`bbox` 同时用于 IoU 匹配，改后两者口径一致。

**教训**：评估工具的**取整实现**必须和文档里写的定义一致，否则同一批数据能得到两个 recall。
这类差异在答辩里会被追问“你到底按哪个口径报的”。

### 11.6 OpenCV 4.5.4 无法加载 YOLO11-pose 的 ONNX（2026-11-08 实测）

想把训练好的 `best.pt` 接进 C++ 主循环，先试 `cv::dnn::readNetFromONNX`，**全部导出变体都失败**：

| 导出配置 | 报错 |
|---|---|
| opset 11 + simplify=True | `shape_utils.hpp:170 total()` 断言失败 |
| opset 11 / 12 / 13 + simplify=False | `onnx_importer.cpp:739 handleNode`：`Add` 节点不支持 |
| opset 11 + dynamic=True | `graph_simplifier.cpp:76`：`Gather` 解析失败 |
| opset 12 + simplify=True | 同第一条断言失败 |

**结论**：与导出参数无关，是 OpenCV 4.5.4（2021 年）的 ONNX 导入器不认识 YOLO11 的图与 pose 头。
升级 OpenCV 4.10 要源码编译 15–25 min 且不保证支持 `Attention/Split`，风险高。

**最终方案：ONNX Runtime**（`libonnxruntime.so` 1.23.2，从 `onnxruntime` 的 Python 包里取），
C API 单头文件即可接入。实测输出 `(1, 26, 8400)` = `4(box) + 14(cls) + 8(4 关键点×2)`。

### 11.7 ONNX Runtime C++ 接入的四个坑（2026-11-08 实测）

| 坑 | 现象 | 正确做法 |
|---|---|---|
| 头文件被拆开 | 只带 `onnxruntime_c_api.h` 报 `onnxruntime_ep_c_api.h: No such file` | 同时取 `onnxruntime_ep_c_api.h`、`onnxruntime_float16.h`（可选 `onnxruntime_cxx_api.h`） |
| SONAME 不匹配 | 链接成功但运行报 `libonnxruntime.so.1: cannot open shared object file` | pip 包只给 `libonnxruntime.so.1.23.2`，需建软链 `libonnxruntime.so.1` 并设 RPATH |
| **通道顺序** | 蓝方板被判成红方（`B3` → `R3`，置信度还不低） | 输入必须是 **RGB**；`cv::split` 后 `std::swap(ch[0], ch[2])` 交换的是 Mat 头、数据不变，**必须先 `cvtColor(BGR2RGB)`** |
| 只换 Mat 头无效 | 同上，swap 后结果毫无变化 | 同上 |

**验证方法**：同一帧上 C++ 与 Python 的类别、置信度必须一致
（实测 `B3 0.771` vs ultralytics `0.77`），时间戳/角点误差再对一遍。

### 11.8 融合补检的两个时间一致性问题（2026-11-09 实测）

背景：为省算力，NN 每 N 帧推理一次，结果缓存。代价是两个**方向相反**的伪影：

**① 缓存坐标被当新目标 → 飘框、重复标签**

非推理帧把上一次推理的框直接加到当前画面：相机一转，旧框就落在空地/别的目标上，
同时出现“同一块板既有 `small` 又有 `B3`”。

修法：**补检只在本帧刚推理时生效**（`infer_now` 判断），非推理帧只把缓存用于类别匹配
（IoU 匹配在天旋地转时会自然失效，不会误标）。

**② 补检只在 1/N 帧生效 → 斜视板闪烁**

极端斜视时单侧灯条被遮挡，传统必然漏检，只能靠 NN 补检；间隔 5 帧时约 6 Hz 闪烁。

**实战取舍：不修。** 理由：
- 闪烁的板处于偏航 > 60°（PnP 位姿误差已不可接受，本就在交战包线外）；
- 唯一修法是提高推理频率，而 ORT 单次 18.6 ms（24 核）会直接吃掉包线内的帧率；
- 正确解法是第四讲跟踪：用时间信息维持目标存在性，且**不需要提高推理频率**。

**性能实测**（`best.onnx`，640 输入，CPU）：

| ORT 线程设置 | 单次推理 |
|---|---|
| `SetIntraOpNumThreads(2)` | 37.6 ms |
| `SetIntraOpNumThreads(4)` | 23.0 ms |
| `SetIntraOpNumThreads(0)`（自动） | **18.6 ms** |
